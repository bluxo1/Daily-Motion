# MVP requirement-to-code matrix

Baseline and evidence interpretation: [project state](PROJECT_STATE_AFTER_PR21.md).
This matrix covers every accepted [PRD](prd.md) ID. A code-complete label does not
mean hardware/provider qualified or publicly enabled. Candidate additions are
explicitly distinguished from the merged baseline.

UI notation: **A** = available for an authorized existing account in debug,
profile/internal and release; **I** = default off, explicit non-product
`DM_LOCAL_ROUTINES` opt-in in debug/profile, excluded in release; **M** = mixed,
with ordinary reads/logging but the creation/authoring path internal. All release
availability also requires valid production configuration. No synthetic Start
action is counted as a verified-user feature.

## Conclusions

At the merged baseline, PRD03/07/08 have substantial complete supported-domain
code and local evidence; PRD02/04/09 and routine parts of05/06 are internally
implemented but unavailable as a complete release journey. PRD10/13 are absent;
01/05/06/11/12/14/15/16/17/18 retain explicit functional or qualification gaps.
No PRD ID is declared fully public-release accepted here. PRD15's new record
subslice is a review candidate; it is not retroactively attributed to PR19/21.

Priority distinguishes blockers from safe work selection: P0 gates must close
before launch, but several require human/provider/hardware decisions. P1 code
work can proceed independently. Detailed proposed PR ordering and preconditions
are in [MVP_EXECUTION_PLAN](MVP_EXECUTION_PLAN.md).
